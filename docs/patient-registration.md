# Account-to-patient lifecycle

Self-signup creates an unverified `User` with a server-assigned `STUDENT` or `FACULTY_STAFF` role. The selected affiliation is stored temporarily in `User.registrationProfile`; it is not a permission grant. Login remains blocked until email verification.

The verification endpoint updates the user, creates or links the patient, writes audit events, and clears the pending profile in one serializable Prisma transaction. A failed patient write rolls back verification so the same link can be retried. A second use of a successfully consumed link is rejected without creating another patient.

`User.patientId` is already unique and points to the separate `Patient` model. A verified email can link an existing, unlinked manual patient of the same type. Other matches require clinic review; neither a name match nor a conflicting account is linked automatically. Student and employee numbers belong to their respective profile models and are never substituted for `Patient.patientNumber`.

New patient numbers use `CLN-<UTC year>-<five-digit sequence>` (for example, `CLN-2026-00001`), generated by the API. A `PatientNumberSequence` row is atomically incremented in the same transaction as patient creation, and MySQL enforces uniqueness on `Patient.patientNumber`. The sequence is initialized from existing numeric CLN IDs by migration; older random and STU/FAC/STF IDs remain unchanged. The five-digit format supports 99,999 new IDs per year. New records can lack clinical details and an institutional number; staff can complete those fields later. The system does not introduce a second status enum for this condition.

Apply the `20260913000000_registration_profile` and `20260913000001_patient_number_sequence` migrations before deploying the API. For existing verified accounts, first run `node node_modules/tsx/dist/cli.mjs scripts/backfill-patient-links.ts` to see a dry-run report. Run the same command with `--apply` to create or link eligible patients. It is rerunnable. Older `FACULTY_STAFF` accounts without an affiliation are reported for manual review, since the shared role cannot distinguish faculty from staff. Do not infer affiliation from a name.

The self-profile endpoint is `GET /api/v1/patients/me`. It derives the patient ID from the authenticated user in the database and grants access only to institutional roles with `own_profile.read`. Staff patient-list permissions are unchanged.
